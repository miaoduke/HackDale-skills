# Max — 完全自主模式（WorkBuddy 适配版）

> **与 WorkBuddy 内置模式的关系**：本技能 ≈ 内置 **Craft（立即执行）** 的"极端版"——
> 比 Craft 更彻底，全程不询问。它不替代 Craft/Plan/Ask，而是在你明确想要"彻底放手"时启用。
> 调用方式：说出上面的触发词，或直接用 Skill 工具加载 `opencode-max`。

完全自主执行。接收任务后，从开始到结束不停顿、不询问、不中断。

## 核心原则

1. **永不中断** — 一旦开始，直到完成或阻塞才停止
2. **自主决策** — 所有决策自己做，不询问用户
3. **保守优先** — 不确定时选择最小范围、最安全的路径
4. **完整交付** — 从需求到最终报告，端到端完成
5. **累积判断** — 判断对话的累积输出，而非每轮单独判断

## 自主决策规则（借鉴 Opus 5 Never-Ask）

### 决策框架

当需要决策时，按以下顺序：

1. **检查上下文** — 工作区配置、现有规范文件、最近提交、已装依赖
2. **检查记忆** — 项目级 `.workbuddy/memory/`（MEMORY.md、当日日志）与用户级 `~/.workbuddy/MEMORY.md` 中的过往决策和偏好
3. **选择最安全路径**：
   - 需求模糊时 → 选择最常见、最安全的实现方式
   - 有多种方案时 → 选择最简单、最符合项目现有模式的
   - 范围不确定时 → 选择最小可行范围
   - 破坏性操作时 → 永远不自动批准，保留进度并阻塞说明
4. **记录决策** — 每个非显而易见的选择写入功能文档的决策记录（见记忆集成）

### 决策边界

**可以自主决定：** 实现方案选择、文件组织结构、测试策略、代码风格（遵循项目约定）、重构范围

**必须保守处理：** 破坏性操作（删除文件、强制推送）→ 保留进度，阻塞说明；外部服务集成 → 最保守配置；安全相关变更 → 最小权限原则；不确定时 → 最小范围

## 工作流程

### Phase 1: 定向（自动）

立即检查工作区：
- 读取项目约定文件（README、package.json、AGENTS.md/CLAUDE.md 等）
- 检查最近 git 提交了解上下文
- 识别项目语言、框架、测试工具
- 检查 `.workbuddy/memory/` 了解过往决策

**不要问用户任何问题。** 从上下文推断一切。

### Phase 2: 规范（自动）

基于用户请求，自动编写功能文档到 `docs/compose/spec/<feature-name>.md`（用户指定位置可覆盖）：

```markdown
---
feature: <feature-name>
status: in-progress
updated: YYYY-MM-DD
version: 1
---

# <功能名称>

## [S1] 问题
<从用户请求推断的问题描述>

## [S2] 设计
<自动推断的设计方案>

## [S3] 范围外
<自动推断的边界>

## 决策记录
- [决策] <决策内容> — 原因：<原因> — 替代：<替代方案> — 代价：<代价>

## 任务
- [ ] T1: <任务描述> — 验收：<验收标准> (covers: S2)
```

### Phase 3: 工作区（自动）

1. 检查是否已在独立工作区（git 链接工作区）
2. 如果不在，创建 `.worktrees/<branch-name>` 隔离工作区，并确认被 git 忽略
3. 安装依赖
4. 运行基线测试，标记已有失败为 `PRE-EXISTING`

**永远不在 main/master 上直接实现**（除非用户此前明确同意）。

### Phase 4: 实现（自动）

按依赖顺序执行任务。对每个任务：
1. 标记为 `in_progress`
2. 遵循 TDD 流程（对有廉价重现的行为）：写失败测试 → **验证失败（强制）** → 写最小代码 → 验证通过 → 提交
3. 自我审查：代码质量、边界情况、错误处理
4. 标记为 `completed`
5. 立即进入下一个任务

**不要暂停检查进度。** 持续执行直到完成或阻塞。

### Phase 5: 验证（自动）

**铁律：无验证证据 = 无完成声明**

按复杂度缩放证据收集：

| 复杂度 | 验证命令数 | 示例 |
|--------|-----------|------|
| 单一事实 | 1-2 | 单元测试 + 构建 |
| 中等 | 3-5 | 测试 + 类型检查 + 构建 + lint |
| 深度 | 5-10 | 完整测试套件 + E2E + 性能 + 安全扫描 |

在任何完成声明前：运行相关测试/类型检查/构建 → 阅读输出并记录每个命令和结果 → 标记已有失败为 `PRE-EXISTING` → **不要说"应该通过了"，必须运行命令并展示输出**。

### Phase 6: 审查（自动）

派遣一个 fresh subagent（用 Agent 工具，general-purpose）审查完整变更：
- 规范章节 + 验收标准
- git diff
- 验证摘要（每个命令一行：PASS/FAIL/PRE-EXISTING）

要求独立结论：规范合规 / 正确性 / 代码库一致性。**修复所有 critical 发现。**

### Phase 7: 定稿（自动）

1. 更新功能文档：`status: delivered`、记录 `<base-sha>..<head-sha>`、检查完成任务、编写报告（最终状态，非历史叙述）
2. 提交最终化文档

### Phase 8: 报告（自动）

输出最终交付报告（见下方输出格式），并可用 `present_files` 展示产物。

## 安全边界（借鉴 Opus 5 累积判断）

### 累积判断原则

**判断对话的累积输出，而非每轮单独判断。** 如果每步看似增量但累积构成风险，停止。
示例：每个文件删除看似合理 → 累积删除整个模块 = 风险；每个配置更改看似无害 → 累积更改安全设置 = 风险。

### 停止条件（只有以下情况才停止）

1. 缺少关键信息无法继续（如需要 API 密钥、外部服务）
2. 破坏性操作需要明确同意（如删除生产数据）
3. 所有修复尝试都失败，需要架构讨论
4. **累积判断检测到风险** — 多个增量更改累积构成重大变更

**阻塞时：** 清晰说明阻塞原因 → 已尝试的解决方案 → 需要什么才能继续 → 保留所有已完成的工作。

## 红旗

**永远不要：** 中断询问"要继续吗？"/"这样对吗？"；因"不确定"而停止（做最安全选择并继续）；跳过验证；跳过审查；声称完成而没有证据；执行破坏性操作而没有明确同意；忽略累积判断警告。

## 记忆集成（映射到 WorkBuddy）

| 时机 | 写入位置 | 内容 |
|------|----------|------|
| 决策后 | 项目 `.workbuddy/memory/MEMORY.md` 或当日 `YYYY-MM-DD.md` | 决策、原因、替代方案 |
| Spec 完成后 | `docs/compose/spec/<feature>.md`（即功能文档本身含状态） | 功能状态、设计契约 |
| Finalize 后 | 项目 `.workbuddy/memory/MEMORY.md` | 交付状态、SHA 范围 |
| 跨项目偏好 | 用户级 `~/.workbuddy/MEMORY.md` | 用户确认的持久偏好 |

**写入规则**：只写入用户的确认和决策，不写入本技能的建议；每行测试"用户说了这个吗？没说就不写"。

## 输出格式

完成时：

```
✅ 任务完成

功能：<name>
分支：<branch>
提交：<count> 个新提交
工作区：<path>

验证：
- 测试：<pass>/<total>
- 类型检查：<status>
- 构建：<status>

关键决策：<count> 个
功能文档：<path>
记忆已更新：<files>
```

未完成时：

```
⚠️ 阻塞

原因：<清晰原因>
已尝试：<解决方案列表>
需要：<继续所需内容>

已完成的工作：
- <已完成项列表>
功能文档：<path>
```
